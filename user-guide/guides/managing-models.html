Managing Models

This guide covers the lifecycle of models in the workspace: what a model file is, how models enter through the import gate, how to inspect and validate them, and how deletion is protected by the dependency graph. Exact flags for every command are in the Command Reference.

Models are code​

A workspace model is a .tsx module (JSX that renders into a model when executed), not a JSON data file:

/** @jsx createExprNode */

import { createExprNode } from '@aelastics/synthesis/jsx'
import type { ExprNode } from '@aelastics/synthesis/jsx'
import type { ModelStore } from '@aelastics/synthesis/store'
import { EERSchema, Entity, Attribute, Domain } from 'eer-metamodel'

export const $synth = {
  kind: 'model',
  metamodel: 'eer-metamodel',
  references: {},
  author: 'Jane Doe <jane@example.org>',
  version: '0.1.0',
  description: 'Persons EER schema'
} as const

export default (store: ModelStore) => (
  <EERSchema name="Persons" store={store}>
    <Entity name="Person">
      <Attribute name="personId" isKey={true}>
        <Domain name="number" />
      </Attribute>
    </Entity>
  </EERSchema>
)

Every workspace model carries an exported $synth header, a pure literal constant that is written and maintained by the tools (model import, transformation run, config init), never required from humans. A hand-authored file without a header gets one derived at import.

FieldMaintained byMeaning
kindtoolsmodel, metamodel, decision-model, binding-model, or configuration-model
metamodeltoolspackage of the metamodel the content instantiates
referencestoolsmap of workspace refs this model depends on (e.g. sourceModel)
generatedBytools{ tx, txVersion, config, date } provenance when produced by a run; null for authored models
createdAt / modifiedAttoolsISO dates, maintained on import and write
authoryou (flags)defaults from git config user.name / user.email, override with --author
versionyou (flags)the model's own semver, default 0.1.0
descriptionyou (flags)one line, shown in model ls and pickers
tagsyou (flags)string list for search and filtering

Commands like model ls, doctor, and shell completion read the header with a fast static parse; model import and transformation run read it authoritatively after loading the module and cross-check it against the rendered content (doctor reports disagreements, doctor --fix re-derives).

Importing: the validation gate​

Everything enters the workspace through model import <file> --as <ref>:

  1. The file is transpiled and rendered into a throwaway store, giving full structural validation. Broken JSX, an unresolvable metamodel, or a dangling $refByName reject the import.
  2. The model's references are checked against the workspace; a missing dependency is an error naming it (in a terminal session, synth offers to import it first).
  3. The $synth header is derived or verified and written; authorship fields are stamped (--author, --description, --tags, defaults from git config).
  4. The file is copied into the namespace tree. --force overwrites an existing target.

The invariant this buys: everything in the workspace was loadable when it entered. That is why run time is strict: --in accepts workspace refs, never file paths.

Inspecting and validating​

synth model ls                    # all models with header metadata
synth model ls --ns com.example   # filtered to one namespace
synth model show com.example/persons       # header and file location
synth model validate com.example/persons   # render for real, check metamodel

model validate also accepts --against <metamodel> to assert the header declares a specific metamodel. Configuration models reference their transformation's decision and binding models, which live in the installed package rather than the workspace; pass --tx <name> so the validation render pre-loads the package's parts.

synth doctor re-checks the import-gate invariant workspace-wide; doctor --fix re-derives missing or unparseable headers through the same code path as model import.

Organizing with namespaces​

synth namespace ls                # list all namespaces
synth namespace mk com.example    # create (dot-separated segments)
synth namespace rm com.example    # remove; must be empty unless --force

namespace rm --cascade additionally deletes every model outside the namespace that transitively references a model inside it (implies --force).

Exporting​

synth model export <ref> [--to <file>] writes a model out to disk, verbatim, header included: the counterpart of model import for sharing a model outside the workspace.

Deleting and the dependency graph​

Deletion is protected by the reverse-dependency graph built from $synth headers: synth model rm <ref> is refused while any other model transitively references the target, and the refusal lists the dependent models. --cascade deletes the target together with every model that transitively references it. config rm has the same semantics for configuration models.
