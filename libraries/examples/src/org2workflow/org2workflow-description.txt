Model-to-Model Transformations in AelasticS Synthesis
======================================================

1. General Concepts
-------------------

A model-to-model (M2M) transformation maps a source model conforming to one
metamodel into a target model conforming to another. In the AelasticS Synthesis
framework, transformations are defined as TypeScript classes that use JSX as
concrete syntax for constructing target model elements. The key concepts are:

Transformation class and @M2M decorator.
  A transformation is a class extending abstractM2M<S, D, EM, CM, P>, where S
  and D are the source and target model types, and P is an optional parameter
  type. The @M2M decorator registers the source and target metamodel schemas
  and initializes the transformation context (trace model, input/output
  descriptors). The class must implement a template(source) method, which
  serves as the top-level transformation rule (r0).

Transformation rules as templates.
  Each transformation rule is a method that accepts a source model element and
  returns a JSX expression constructing target model elements. The JSX is not
  rendered to DOM -- it produces Element instances that the framework renders
  into typed model objects managed by a ModelStore. Rules are therefore model
  templates parameterized by source elements.

Element-to-element rules and @E2E decorator.
  The @E2E decorator marks a method as an element-to-element rule, specifying
  its input and output types. When invoked, the decorator intercepts the call
  to record a trace link from the source element to the target JSX element,
  enabling full traceability between source and target models.

Polymorphic dispatch via @SpecPoint and @SpecOption.
  The @SpecPoint decorator marks a rule as a specialization point -- a rule
  whose behavior varies depending on the runtime type of its input element.
  The @SpecOption decorator registers a specialized rule for a specific input
  subtype. At runtime, the framework inspects the actual type of the source
  element (via the ModelStore's type registry) and dispatches to the matching
  specialized rule. The base rule marked with @SpecPoint produces an abstract
  target element, and the selected @SpecOption produces a concrete sub-element
  that refines or replaces it. This achieves type-safe polymorphic dispatch
  without explicit conditional logic.

Iterative generation.
  Rules may use standard functional combinators (.map(), .filter()) over
  collections of source elements to generate a variable number of target
  elements within a single JSX expression. This is the kappa (k) operator
  in the formal model.

Parameterized transformations.
  The abstractM2M base class accepts a generic parameter type P. A value of
  type P is passed to transform(source, param) and becomes accessible as
  this.context.param within all rules. This allows the same transformation
  class to produce structurally different target models depending on
  external parameters, without modifying the transformation definition.


2. The OrgModel to ApprovalWorkflow Transformation
---------------------------------------------------

This transformation generates a personalized document approval workflow from
an organizational hierarchy. Given a worker and a sensitivity level, it
produces a sequential workflow where the document passes through approval
steps at each level of the organization above the worker, up to the
specified depth.

Parameters.
  The transformation is parameterized by ITransformParam, which carries:
  - worker: the Worker initiating the document
  - sensitivity: an integer controlling how many hierarchy levels require
    approval (1 = immediate department, 2 = up to division, 3 = up to board)

Top-level rule: template(source).
  The template method implements the transformation logic in three steps:

  (a) Hierarchy traversal. A recursive function unfold(unit, levels) starts
      from the worker's department (obtained via worker.worksIn) and follows
      parent links upward, collecting at most `sensitivity` OrgUnit instances.
      This produces an ordered list of organizational units requiring approval.

  (b) Target model construction. The method returns a JSX expression that
      builds a WorkflowModel containing a single Process. The process flow
      is a Sequence whose first step is a "WriteDocument" Task assigned to
      the worker, followed by the approval steps generated by mapping the
      collected OrgUnits through the polymorphic rule OrgUnit2Approval.

  (c) Polymorphic approval generation. Each OrgUnit in the collected list
      is passed to OrgUnit2Approval, which dispatches to the appropriate
      specialized rule based on the unit's runtime type.

Polymorphic rule: OrgUnit2Approval.
  This rule is marked with @SpecPoint and @E2E({input: OrgUnit, output: Step}).
  It serves as the abstract base rule. Two specializations are registered:

  - Department2Approval (@SpecOption for Department): produces a single Task
    element with the department's manager as performer. This represents
    sequential approval by one person -- the department head.

  - Board2Approval (@SpecOption for Board): produces a Parallel element
    containing one Task per board member, each with the member's name as
    performer. This represents concurrent approval by all board members.

  The polymorphic dispatch is automatic: the framework determines whether
  each OrgUnit is a Department or a Board at runtime and invokes the
  corresponding specialization. No conditional branching (if/switch)
  appears in the transformation code.

Example execution.
  For worker Judy (member of Engineering department) with sensitivity=3,
  the unfold function collects: [Engineering, Technology Division,
  Executive Board]. The transformation produces:

    WorkflowModel "Approval"
      Process "ApprovalForJudy"
        Sequence "ApprovalSequence"
          Task "WriteDocument"          performer: Judy
          Task "ApproveByGrace"         performer: Grace    (Engineering manager)
          Task "ApproveByDave"          performer: Dave     (Technology Division manager)
          Parallel "BoardApproval"
            Task "ApproveByAlice"       performer: Alice    (Board member)
            Task "ApproveByBob"         performer: Bob      (Board member)
            Task "ApproveByCarol"       performer: Carol    (Board member)

  With sensitivity=1, only [Engineering] is collected, producing just the
  WriteDocument task followed by a single approval by Grace.

Trace model.
  The framework automatically constructs a trace model that records the
  correspondence between source and target elements. The @M2M decorator
  creates an M2M_Trace model instance linking the source Organization to
  the target WorkflowModel. Each invocation of an @E2E-decorated rule
  records an E2E_Trace element that maps a source model element to the
  target element(s) it produced. The trace is built transparently -- the
  transformation author writes only the mapping rules, and the decorator
  infrastructure intercepts each rule invocation to record the trace link.

  For the Judy/sensitivity=3 example, the trace model contains:

    M2M_Trace "Acme Corp to Approval"
      from: Organization "Acme Corp"
      to:   WorkflowModel "Approval"
      instanceOf: Org2WorkflowTransformation

      E2E_Trace "Engineering to ApproveByGrace"
        from: Department "Engineering"
        to:   Task "ApproveByGrace"
        instanceOf: OrgUnit2Approval

      E2E_Trace "Technology Division to ApproveByDave"
        from: Department "Technology Division"
        to:   Task "ApproveByDave"
        instanceOf: OrgUnit2Approval

      E2E_Trace "Executive Board to BoardApprovalExecutiveBoard"
        from: Board "Executive Board"
        to:   Parallel "BoardApprovalExecutiveBoard"
        instanceOf: OrgUnit2Approval

  Each E2E_Trace records which rule produced it (instanceOf points to the
  OrgUnit2Approval rule type in the transformation type model). This
  enables bidirectional navigation: given any target element, one can
  trace back to the source element and the rule that produced it, and
  vice versa. The trace model is itself a model conforming to the trace
  metamodel, and can be persisted, queried, or used for incremental
  re-transformation when the source model changes.

Summary of demonstrated concepts.
  - Parameterized transformation: sensitivity controls output structure
  - Polymorphic dispatch: Department and Board produce structurally different
    target patterns through @SpecPoint/@SpecOption without conditionals
  - Iterative generation: Board2Approval uses .map() over members to produce
    a variable number of parallel tasks; template uses .map() over the
    collected hierarchy to chain approval steps
  - Templates as rules: every rule is a method returning JSX, confirming
    that transformation rules are model templates parameterized by source
    elements and external parameters
