2. The generator

The whole transformation is one class in src/transformation.tsx, and every listing below is taken from examples/tutorial/sql-tutorial-basic/src/transformation.tsx.

The file opens the way every JSX authoring file does, with the pragma and the imports:

/** @jsx createExprNode */

import { createExprNode } from '@aelastics/synthesis/jsx'
import type { ExprNode } from '@aelastics/synthesis/jsx'
import { abstractM2M } from '@aelastics/synthesis/m2m'
import { M2T, Doc, Sec, P } from '@aelastics/synthesis/m2t'
import type { ModelStore } from '@aelastics/synthesis/store'
import * as m2tmm from '@aelastics/synthesis/m2t'
import * as rmT from 'rel-tutorial-metamodel/model'

The asymmetry is the same as in any transformation, only the addresses have changed. From the source metamodel it imports the /model subpath alone: rmT gives the interfaces to type against and the type objects to test elements with. Everything the target needs comes from @aelastics/synthesis/m2t: the tags M2T, Doc, Sec, and P for building, and the m2tmm namespace for the interfaces.

Notice that there is no import of any target components package. In a model-to-model transformation the target tags come from the target metamodel's package. Here they are part of the library's text side, because the engine is what turns the resulting model into files.

The class​

export class RelToSqlBasicTransformation extends abstractM2M<rmT.IRelSchema, m2tmm.M2T_Model> {
  constructor(store: ModelStore) {
    super(store)
  }

This is the line worth pausing on for a moment. The base class is abstractM2M, the same one the model-to-model tutorial used, with the same two type parameters. The transformation is a function from a relational schema to an M2T_Model, and there is no abstractM2T to extend and no generator interface to implement.

What makes the package a text generator is declared in the manifest, not in the class: "kind": "m2t" tells the CLI to run the engine's text generation on the result and write files, instead of serializing the result back into the workspace. Page 3 shows it. If you ever wondered whether text generation in Synthesis is a special execution mode, this is the answer: it is the ordinary one, pointed at a different target.

template(): one document is one file​

  // One <Doc> means one file. Its name is the file name the CLI writes,
  // so the schema name carries straight through to Library_rel.sql.
  template(s: rmT.IRelSchema) {
    return (
      <M2T name={`${s.name}_sql`}>
        <Doc name={`${s.name}.sql`}>
          <Sec name="header">
            <P>{`-- SQL DDL generated by Synthesis from ${s.name}`}</P>
            <P>{' '}</P>
          </Sec>
          {this.tablesOf(s).map((tab) => this.tableToCreate(s, tab))}
        </Doc>
      </M2T>
    )
  }

Read it as three decisions.

The output root. <M2T> is the result model, and its name is a model name like any other. It never appears in the output; only documents become files.

One document. The single <Doc> is the entire file structure of Part 1, and its name is built from the schema's name, so the schema named Library_rel produces Library_rel.sql. Part 2 adds a second <Doc> and gets a second file, with nothing else about the mechanism changing.

Content in emission order. The header section is written first and comes out first; the table sections are appended by the map and come out in the order the tables appear in the schema. Nesting is placement here: a rule's output ends up where the rule was called. That is perfectly workable for one file with one kind of content, and it is exactly what Part 2 replaces, because it forces every rule to be written where its output belongs.

The store is not passed to <M2T> in this template, and it does not need to be: abstractM2M supplies the execution context, and the root picks the store up from there. this.context.store is still used below, to ask elements what type they are.

Tables become CREATE TABLE statements​

  // A section groups the paragraphs of one statement. Sections nest
  // directly in the document here, so the file follows the order the
  // template emits them in; Part 2 replaces that order with named
  // placement.
  tableToCreate(s: rmT.IRelSchema, tab: rmT.ITable): ExprNode<m2tmm.ISection> {
    const cols = tab.columns ?? []
    return (
      <Sec name={`table_${tab.name}`}>
        <P>{`CREATE TABLE ${tab.name} (`}</P>
        {cols.map((c, i) => (
          <P>{`  ${this.columnLine(s, c)}${i < cols.length - 1 ? ',' : ''}`}</P>
        ))}
        <P>{');'}</P>
        <P>{' '}</P>
      </Sec>
    )
  }

One statement, four kinds of line: the opening line, one line per column, the closing );, and the separator. Each is a <P>, and each <P> is exactly one line in the file.

The section is the reason this rule can be one function. A rule returns one value, and a CREATE TABLE statement is several lines, so the lines need a container. As page 1 explained, that container contributes no text of its own: strip the sections out, emit the paragraphs directly into the document, and the generated file is byte for byte the same. What the section buys is a name, which Part 2 turns into an address.

Two details of the formatting are worth calling out, because they are where beginners expect the framework to help and it does not.

The comma placement is arithmetic. ${i < cols.length - 1 ? ',' : ''} puts a comma after every column line except the last. There is no list separator facility; a separator is a character you append.

The indent is in the string. The two leading spaces of a column line are written in the template literal. The engine has no notion of indentation level.

Columns become lines​

  // Every clause of a column definition comes from one property of the
  // column: there is no hidden state and no lookup table.
  private columnLine(s: rmT.IRelSchema, c: rmT.IColumn): string {
    const parts: string[] = [c.name, c.type]
    if (c.isKey) {
      parts.push('PRIMARY KEY')
    }
    if (c.isAutoincrement) {
      parts.push('AUTOINCREMENT')
    }
    if (!c.isNullable) {
      parts.push('NOT NULL')
    }
    // A column is a foreign key exactly when it references another
    // column; the metamodel keeps no separate flag that could disagree.
    if (c.references) {
      parts.push(`REFERENCES ${this.tableOwning(s, c.references).name}(${c.references.name})`)
    }
    return parts.join(' ')
  }

This method returns a string, not an ExprNode, and that division of labour is the one to copy into your own generators. JSX gives you the structure of the output: which files exist, which regions they have, which lines they contain. Ordinary TypeScript gives you the content of a line. A generator that tried to express PRIMARY KEY AUTOINCREMENT NOT NULL as nested tags would be harder to read than the string that produces it, and no more checkable.

Every clause comes from one property, in a fixed order, with no defaults and no lookup table. bookId is isKey, isAutoincrement, and not nullable, so it becomes:

  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,

The last if is where the source metamodel's design pays off. There is no isForeignKey flag to consult: a column is a foreign key exactly when references is present, so the presence of the link is the condition. Part 2 removes this branch and moves the clause into its own file.

Finding the tables​

  // Tables are the schema's model elements, so they are found by type
  // rather than by a dedicated property.
  private tablesOf(s: rmT.IRelSchema): rmT.ITable[] {
    return s.elements.filter((el) => this.context.store.isTypeOf(el, rmT.Table)) as rmT.ITable[]
  }

A RelSchema declares no tables property. Its tables are top-level model elements, so they are found by filtering s.elements on their type, exactly as the model-to-model tutorial's template selects entities and relationships. store.isTypeOf compares against the type object the metamodel package exported, and the as cast afterwards is the TypeScript side of a runtime check.

A REFERENCES clause needs the other table's name​

  // A column does not know its table: the reference goes one way, from
  // the foreign key to the primary key column it points at. The table a
  // REFERENCES clause has to name is therefore the one table in the
  // schema whose columns contain that column.
  private tableOwning(s: rmT.IRelSchema, col: rmT.IColumn): rmT.ITable {
    const owner = this.tablesOf(s).find((tab) => (tab.columns ?? []).some((c) => c.name === col.name))
    if (!owner) {
      throw new Error(`Column '${col.name}' is referenced but belongs to no table of schema '${s.name}'`)
    }
    return owner
  }

SQL wants REFERENCES Author(authorId): a table name and a column name. The model gives the rule only half of that directly. A foreign key column's references link points at the authorId column, and a column has no back link to its table, so the table name has to be found: it is the one table in the schema whose columns contain that column.

That is model navigation, not a workaround. The metamodel stores the fact once, in the direction that matters, and everything else is derived from it. Half of writing a generator is this kind of walk: the target syntax wants information grouped differently from the way the source model stores it, and the generator is where the regrouping happens.

The throw is the same judgement the model-to-model tutorial made about entities without keys. A referenced column that belongs to no table means the model is inconsistent, and there is no honest clause to emit, so the run fails naming the column rather than producing SQL that will not apply.

What is missing from this class​

Compare it against a model-to-model transformation and the interesting thing is what is not there. No target components import, no $refByName on the output side, no ordering constraint between passes, and no serialization concern. A text target is a tree, built once, from the root down, and nothing in it points at anything else.

That is why Part 1 has three pages instead of five: with the shared mechanics already known from the model-to-model tutorial, the distinctly text-shaped part of a generator is small.
