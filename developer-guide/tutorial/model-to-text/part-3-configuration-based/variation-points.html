2. Variation points

The design space is declared. This page is the half that reads it: a template that decides nothing, three options that each build a complete output model, a second variation point three lines long, and the manifest entry that ties the package together.

Every listing is from examples/tutorial/sql-tutorial-configuration-based.

The class becomes decision-aware​

Parts 1 and 2 both opened with a bare class extending abstractM2M with two type parameters. Part 3 changes the base class, adds two type parameters, and puts a decorator on the class:

@M2M()
export class RelToSqlConfigurableTransformation extends DecisionAwareM2M<
  rmT.IRelSchema,
  m2tmm.M2T_Model,
  {},
  cm.IConfigurationModel
> {
  // A configuration-based transformation takes the run's configuration
  // model as a third argument. It is optional: without one, every
  // variation point falls back to its @Default option.
  constructor(store: ModelStore, extra?: {}, configModel?: cm.IConfigurationModel) {
    super(store, extra ?? {}, configModel)
  }

The four type parameters are the source model type, the target model type, a slot for extra arguments (empty here), and the configuration model type. The target is m2tmm.M2T_Model, exactly as in Parts 1 and 2: nothing about generating text changes because the transformation became configuration-based.

@M2M() reads oddly on a package whose manifest says "kind": "m2t". It is not a mistake. A text generator is a model-to-model transformation whose target metamodel happens to be the engine's text metamodel, which is the observation Part 1 opened with, and the decorator machinery does not distinguish the two kinds.

The configModel argument is optional, and that is not a convenience. It is what lets the same class run with no configuration model at all, which is the path page 3's --default-configs run takes.

The imports the new machinery needs, alongside the ones Parts 1 and 2 already had:

import { M2M } from '@aelastics/synthesis/m2m'
import { DecisionAwareM2M, VarPoint, VarOption, Default, Option } from '@aelastics/synthesis/variability'
import * as cm from '@aelastics/synthesis/metamodels/configuration/model'

Option in the second line is a predicate builder, not the <Option /> tag page 1 used to declare options in the decision model. The two never appear in the same file.

A template that decides nothing​

In Parts 1 and 2, template was the whole transformation: it built the <M2T> model, declared the documents, and either emitted sections in place or placed them by name. Here it does one thing:

  // The template does nothing but hand over to the variation point. The
  // decision is the first thing the transformation makes, because
  // everything else depends on it.
  template(s: rmT.IRelSchema): ExprNode<rmT.IRelSchema, m2tmm.M2T_Model> {
    return this.documentLayout(s)
  }

That single line is where the global issue's timing shows up in the code. Page 1 argued that OutputLayout cannot be an element issue because it decides how many documents exist, and this is the shape that argument takes: the layout is resolved before any document is created, because resolving it is creating them.

The layout point and its three options​

  // The variation point. Its body never runs: the dispatcher looks up
  // the option selected for the OutputLayout issue in the run's
  // configuration model and calls that method instead.
  @VarPoint('OutputLayout')
  documentLayout(s: rmT.IRelSchema): ExprNode<rmT.IRelSchema, m2tmm.M2T_Model> {
    throw new Error('Not implemented VarOptions for VarPoint OutputLayout')
  }

  // Part 1's shape: everything in one file, references inline. The
  // simplest thing to read, and correct as long as the tables can be
  // ordered so that no reference points forward.
  @VarOption('documentLayout', Option('SingleFile'))
  singleFileLayout(s: rmT.IRelSchema): ExprNode<rmT.IRelSchema, m2tmm.M2T_Model> {
    return (
      <M2T name={`${s.name}_sql`}>
        <Doc name={`${s.name}.sql`}>
          {this.headerSection('header', `-- SQL DDL generated by Synthesis from ${s.name}`)}
          {this.tablesOf(s).map((tab) => this.tableToCreate(s, tab, true))}
        </Doc>
      </M2T>
    )
  }

  // Part 2's shape, and the default. Foreign keys can be circular, so
  // creating every table before constraining any of them is the only
  // structure that always applies cleanly.
  //
  // @Default matches isDefault on TablesAndConstraints in the decision
  // model: with no configuration model at all, the dispatcher falls back
  // to this option instead of throwing.
  @Default()
  @VarOption('documentLayout', Option('TablesAndConstraints'))
  tablesAndConstraintsLayout(s: rmT.IRelSchema): ExprNode<rmT.IRelSchema, m2tmm.M2T_Model> {
    return (
      <M2T name={`${s.name}_sql`}>
        <Doc name={`${s.name}.sql`}>
          {this.headerSection('header', `-- Tables of ${s.name}, generated by Synthesis`)}
          {this.tablesOf(s).map((tab) => this.tableToCreate(s, tab, false))}
        </Doc>
        {this.constraintsDocument(s)}
      </M2T>
    )
  }

  // One file per table, plus the shared constraints file. The layout a
  // schema-per-directory repository wants, where each table is reviewed
  // and versioned on its own.
  @VarOption('documentLayout', Option('FilePerTable'))
  filePerTableLayout(s: rmT.IRelSchema): ExprNode<rmT.IRelSchema, m2tmm.M2T_Model> {
    return (
      <M2T name={`${s.name}_sql`}>
        {this.tablesOf(s).map((tab) => (
          <Doc name={`${tab.name}.sql`}>
            {this.headerSection(
              `header_${tab.name}`,
              `-- Table ${tab.name} of ${s.name}, generated by Synthesis`
            )}
            {this.tableToCreate(s, tab, false)}
          </Doc>
        ))}
        {this.constraintsDocument(s)}
      </M2T>
    )
  }

The decorators are the ones the model-to-model tutorial's page on variation points explains: @VarPoint(issue) names the issue this rule resolves, @VarOption(pointMethod, predicate) registers a method as one answer at that point, and @Default() sits directly above a @VarOption() to mark the fallback. documentLayout throws because its body is never executed; the dispatcher replaces the call rather than delegating to it, so the throw is a guard against a misconfigured class rather than a reachable path.

What is specific to text generation is the return type. Each option returns an ExprNode<rmT.IRelSchema, m2tmm.M2T_Model>, which is to say a whole output model, <M2T> root included. The dispatch does not pick a fragment that gets merged into a document somebody else declared. It picks the entire document tree, and since one <Doc> becomes one file, picking the tree is picking the files.

Read the three side by side and the differences are small and structural:

  • singleFileLayout declares one <Doc>, gives it Part 1's header line, and passes true for inline references. There is no constraints document, because the references are still in the column definitions.
  • tablesAndConstraintsLayout declares the same <Doc> with Part 2's header, passes false, and adds constraintsDocument(s) alongside it.
  • filePerTableLayout maps over the tables instead of nesting them, producing one <Doc> per table with a per-table header, and adds the same constraintsDocument(s).

Everything else, the CREATE TABLE lines, the column clauses, the ALTER TABLE statements, is shared.

The pieces the options are built from​

The rules that produce statements carry no decorators at all:

  headerSection(name: string, comment: string): ExprNode<m2tmm.ISection> {
    return (
      <Sec name={name}>
        <P>{comment}</P>
        <P>{' '}</P>
      </Sec>
    )
  }

  tableToCreate(s: rmT.IRelSchema, tab: rmT.ITable, inlineReferences: boolean): ExprNode<m2tmm.ISection> {
    const cols = tab.columns ?? []
    return (
      <Sec name={`table_${tab.name}`}>
        <P>{`CREATE TABLE ${this.quoteIdentifier(tab.name)} (`}</P>
        {cols.map((c, i) => (
          <P>{`  ${this.columnLine(s, c, inlineReferences)}${i < cols.length - 1 ? ',' : ''}`}</P>
        ))}
        <P>{');'}</P>
        <P>{' '}</P>
      </Sec>
    )
  }

  // The constraints file only exists in the layouts that took the
  // references out of the CREATE TABLE statements.
  constraintsDocument(s: rmT.IRelSchema): ExprNode<m2tmm.IDocument> {
    return (
      <Doc name={`${s.name}-constraints.sql`}>
        {this.headerSection(
          'constraints-header',
          `-- Foreign key constraints of ${s.name}, generated by Synthesis`
        )}
        {this.foreignKeysOf(s).map((fk) => this.foreignKeyToAlter(fk))}
      </Doc>
    )
  }

The comment above the class's section builders states the line the whole design rests on:

  // The pieces every layout is built from. They are ordinary rules: the
  // decision is about which documents exist and what goes in them, not
  // about how a CREATE TABLE statement looks.

That line is worth defending, because there is an obvious temptation to cross it. tableToCreate takes a boolean:

  tableToCreate(s: rmT.IRelSchema, tab: rmT.ITable, inlineReferences: boolean)

A boolean parameter looks like a decision waiting to be declared, and it is not one. Whether references are inline is entirely determined by the layout: SingleFile has nowhere else to put them, and the other two layouts have a constraints file precisely so that they do not need them inline. Declaring InlineReferences as a second issue would create a configuration that can ask for a single file with no references in it at all, which generates broken DDL, or for a constraints file whose constraints are also inline, which generates duplicates. The parameter is a consequence of the layout, so it is passed as an argument by the option that already knows the answer.

This is the same line the model-to-model tutorial drew when it left the M:N branch of its relationship rule as a plain if. A design space should contain the answers somebody might defensibly want, and nothing else.

A second point, three lines per option​

Identifier quoting goes through the same mechanism at a fraction of the size:

  @VarPoint('IdentifierQuoting')
  quoteIdentifier(name: string): string {
    throw new Error('Not implemented VarOptions for VarPoint IdentifierQuoting')
  }

  @Default()
  @VarOption('quoteIdentifier', Option('Unquoted'))
  unquotedIdentifier(name: string): string {
    return name
  }

  @VarOption('quoteIdentifier', Option('DoubleQuoted'))
  doubleQuotedIdentifier(name: string): string {
    return `"${name}"`
  }

Three things are worth noticing.

It takes a string and returns a string. A variation point is a method, and nothing requires a method to take a model element or return an ExprNode. quoteIdentifier is called with tab.name and with column names, and what it returns goes into a template literal.

It is called from inside the other point's options. The call chain for a CREATE TABLE line is documentLayout, dispatched to one of the three layout options, which calls tableToCreate, which calls quoteIdentifier, which is dispatched again. Two variation points compose without either knowing the other exists, because each one only knows its own issue name and the configuration answers both.

Its default is Unquoted, matching isDefault in the decision model. The same agreement tablesAndConstraintsLayout maintains, one issue down.

Page 3 shows the composition working: FilePerTable with DoubleQuoted puts quoted SQL inside files whose names stay unquoted, because a file name is not a SQL identifier and never passes through quoteIdentifier.

No @E2E here​

The model-to-model tutorial's variation point carried @E2E() above @VarPoint(), and stated the rule that the two can only be stacked in that order. Neither point in this class carries it.

@E2E is optional, and it earns its place when a rule maps one source element to one target element, because that is the pair it records in the trace. Neither of these rules does. documentLayout maps the schema root to the entire output model, and quoteIdentifier maps a string to a string with no model element in sight. The decorator's placement rule still holds if you ever add it; it just does not come up here.

The manifest​

The last change is synth.json. Everything Parts 1 and 2 had is unchanged, and a parts block is added:

{
  "kind": "m2t",
  "entry": "./dist/transformation.js",
  "exportName": "RelToSqlConfigurableTransformation",
  "source": {
    "metamodel": "rel-tutorial-metamodel"
  },
  "target": {
    "metamodel": "text"
  },
  "parts": {
    "metamodels": [
      {
        "module": "rel-tutorial-metamodel/as-model",
        "exportName": "RelTutorialMetamodel"
      }
    ],
    "decisionModel": {
      "module": "./dist/decision-model.js",
      "exportName": "SqlGenerationIssues"
    },
    "bindingModel": {
      "module": "./dist/binding-model.js",
      "exportName": "RelTutorialSqlBindings"
    }
  }
}

"target": { "metamodel": "text" } is Parts 1 and 2's, untouched. The parts block is identical in shape to the model-to-model package's, and the rules are the same ones its page 3 states: the decision and binding model entries name compiled modules in dist, so a change to either source needs a rebuild, while the metamodel-as-model entry is the metamodel package's own as-model subpath; the parts are rendered into the store in the order written, metamodels first, then the decision model, then the binding model, because the binding model's absolute paths point at both; and the decision model and the binding model are declared together, even when, as here, one of them is empty.

Their presence is the whole declaration. Nothing in the manifest says a transformation is configuration-based, and nothing needs to: a parts block with a decision model and a binding model in it is the statement. Page 3 shows the CLI reading it back as variability: yes and shows what that changes about a run.
