3. Running the layouts

The package is complete: a template that hands over to a variation point, three options that each build a whole document tree, a second point wrapping identifier emission, and a decision model saying what may be asked. This page installs it and generates the same four-table schema five different ways.

The build and install loop is Parts 1 and 2's, with the same sample schema:

npm run build

synth init
synth namespace mk demo
synth model import sample/library-rel.tsx --as demo/schema
synth transformation install .
Imported demo/schema
Installed transformation 'sql-tutorial-configuration-based@0.1.0' (m2t) to ~/.synth/transformations/sql-tutorial-configuration-based

What the CLI sees in the package​

synth transformation show sql-tutorial-configuration-based
Transformation: sql-tutorial-configuration-based
  version: 0.1.0
  description: Model-to-text tutorial Part 3 companion: output layout and identifier quoting decided by a configuration model
  kind: m2t
  source metamodel: rel-tutorial-metamodel
  target metamodel: text
  variability: yes
  entry: ./dist/transformation.js (export: RelToSqlConfigurableTransformation)
  parts:
    metamodel: rel-tutorial-metamodel/as-model (export: RelTutorialMetamodel)
    decision model: ./dist/decision-model.js (export: SqlGenerationIssues)
    binding model: ./dist/binding-model.js (export: RelTutorialSqlBindings)
  author: Sinisa Neskovic
  license: Apache-2.0
  path: ~/.synth/transformations/sql-tutorial-configuration-based

Two things are new relative to Parts 1 and 2. variability: yes is derived rather than declared: it is the parts block read back, and a decision model plus a binding model being present is what makes it yes. The parts listing below it names the three modules page 2 added.

What show reports is the manifest, not its contents. It names the three part modules; it does not open them, so it lists neither the two issues nor their five options nor which two are the defaults. Those come from elsewhere: config init writes them into a configuration model, config show prints them back, and every run announces the decisions it took. All three appear below.

A decision is never applied silently​

Run it the way Parts 1 and 2 taught you, with no mention of configuration at all:

synth transformation run sql-tutorial-configuration-based \
  --in demo/schema --out-dir ./generated
Error: Transformation 'sql-tutorial-configuration-based' is
configuration-based. Provide --config <ref> (create one with: synth
config init sql-tutorial-configuration-based --for demo/schema) or
accept generated defaults explicitly with --default-configs.

The run stops with exit code 2, before any engine work. Nothing was loaded, nothing was generated, and ./generated was not created.

The model-to-model tutorial's page on running with configurations explains why the refusal is a design position rather than a missing feature, and the argument is if anything sharper here. The three layouts are not variations on a theme: one of them writes a single file, another writes five, and a build script that expected one and got the other fails somewhere far from the cause. So the run demands consent, in one of two forms: name a configuration you wrote, or say explicitly that generated defaults are acceptable this time. In an interactive terminal the same policy appears as a prompt offering those two paths and an abort.

Running on generated defaults​

synth transformation run sql-tutorial-configuration-based \
  --in demo/schema --default-configs --out-dir ./generated
Running sql-tutorial-configuration-based@0.1.0 (m2t) on demo/schema
decision OutputLayout -> TablesAndConstraints (default)
decision IdentifierQuoting -> Unquoted (default)
Wrote <out-dir>/Library_rel.sql
Wrote <out-dir>/Library_rel-constraints.sql

Each Wrote line carries the absolute path of the file, shortened to <out-dir> here and below.

Two decisions, two lines, and no element named in either of them. That is the shape page 1 promised: the same two lines appear for this four-table schema and for a schema of any size, because both issues are global. (default) marks that nobody chose the option explicitly.

The two files are the ones the default layout declares:

-- Tables of Library_rel, generated by Synthesis
 
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER
);
 
CREATE TABLE Author (
  authorId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  authorName VARCHAR(255)
);
 
CREATE TABLE Category (
  categoryId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  categoryName VARCHAR(255)
);
 
CREATE TABLE categorizedAs (
  BookId_FK INTEGER NOT NULL,
  CategoryId_FK INTEGER NOT NULL
);

and Library_rel-constraints.sql, whose one-line header is followed by one ALTER TABLE statement per foreign key:

-- Foreign key constraints of Library_rel, generated by Synthesis
 
ALTER TABLE Book ADD CONSTRAINT fk_Book_AuthorId_FK
  FOREIGN KEY (AuthorId_FK) REFERENCES Author(authorId);
 
ALTER TABLE categorizedAs ADD CONSTRAINT fk_categorizedAs_BookId_FK
  FOREIGN KEY (BookId_FK) REFERENCES Book(bookId);
 
ALTER TABLE categorizedAs ADD CONSTRAINT fk_categorizedAs_CategoryId_FK
  FOREIGN KEY (CategoryId_FK) REFERENCES Category(categoryId);

Compare that with what Part 2 wrote. Library_rel.sql is byte for byte identical, and the constraints file differs only in its header: Part 2 declared its documents once and could afford two extra comment lines explaining the deployment order, while Part 3's shared constraintsDocument builds one header for three different layouts and keeps it to one line. The statements are the same. A layout that used to be the transformation is now one option of it.

An editable configuration​

--default-configs accepted a configuration the run built in memory and discarded. config init builds the same one and saves it:

synth config init sql-tutorial-configuration-based --for demo/schema
decision OutputLayout -> TablesAndConstraints (default)
decision IdentifierQuoting -> Unquoted (default)
Wrote demo/schema-cfg (~/.synth/models/demo/schema-cfg.tsx)

Same two lines, because it is the same generation. Without --out the result lands at <namespace>/<name>-cfg.

A configuration model is a workspace model like any other, a .tsx file with a $synth header whose kind is configuration-model. Below the header:

export default (store) => (
  <ConfigurationModel
    name="Library_relDefaultConfigurationModel"
    sourceModel={<Model $refByName="//www.aelastics.org/Library_rel" />}
    bindingModel={<BindingModel $refByName="//www.aelastics.org/RelTutorialSqlBindings" />}
    store={store}
  >
    <GlobalChoice
      name="gc_OutputLayout"
      choices={[
        <Choice
          name="gc_OutputLayout_TablesAndConstraints"
          issue={<GlobalIssue $refByName="//www.aelastics.org/SqlGenerationDesign/OutputLayout" />}
          selectedOption={<Option $refByName="//www.aelastics.org/SqlGenerationDesign/TablesAndConstraints" />}
        />,
      ]}
    />
    <GlobalChoice
      name="gc_IdentifierQuoting"
      choices={[
        <Choice
          name="gc_IdentifierQuoting_Unquoted"
          issue={<GlobalIssue $refByName="//www.aelastics.org/SqlGenerationDesign/IdentifierQuoting" />}
          selectedOption={<Option $refByName="//www.aelastics.org/SqlGenerationDesign/Unquoted" />}
        />,
      ]}
    />
  </ConfigurationModel>
)

This is the whole file, and it is worth pausing on how short it is. The model-to-model tutorial's configuration held an <ElementChoice> per source element that raised its issue, so it grew with the model. This one holds a <GlobalChoice> per issue, so it has two of them for Library_rel and would have two of them for a schema of four hundred tables. That is the practical payoff of a global issue: the whole design space of this generator fits on a screen, and a reviewer can see every decision it took at once.

Every path in the file was introduced earlier. //www.aelastics.org/Library_rel is the source schema. //www.aelastics.org/RelTutorialSqlBindings is page 1's binding model, named here so that a configuration can only be used with the transformation it was generated for. The two //www.aelastics.org/SqlGenerationDesign/... pairs are the issue and the selected option from the decision model.

config show prints the same content as decisions:

synth config show demo/schema-cfg
Ref:          demo/schema-cfg
Path:         ~/.synth/models/demo/schema-cfg.tsx
Tx:           sql-tutorial-configuration-based
Source model: demo/schema
Generated:    by sql-tutorial-configuration-based@0.1.0 on 2026-08-29T05:21:18.950Z
Decisions:
  decision OutputLayout -> TablesAndConstraints (default)
  decision IdentifierQuoting -> Unquoted (default)

Switching an option​

Changing a layout is a two-line edit inside one <Choice>, and synth config edit demo/schema-cfg opens the file in $EDITOR if you prefer:

- name="gc_OutputLayout_TablesAndConstraints"
- selectedOption={<Option $refByName="//www.aelastics.org/SqlGenerationDesign/TablesAndConstraints" />}
+ name="gc_OutputLayout_SingleFile"
+ selectedOption={<Option $refByName="//www.aelastics.org/SqlGenerationDesign/SingleFile" />}

The selectedOption line is the decision. The name line is cosmetic: the generator names a choice after the option it holds, and a file that says TablesAndConstraints while selecting SingleFile will mislead somebody later. The issue={<GlobalIssue ... />} line is never touched, because the question has not changed, only the answer.

Check that the file still renders before running it:

synth model validate demo/schema-cfg --tx sql-tutorial-configuration-based
[ok] file transpiles and imports
[ok] default export renders (with 'sql-tutorial-configuration-based' context)
[ok] $synth header present
Model demo/schema-cfg is valid

SingleFile​

synth transformation run sql-tutorial-configuration-based \
  --in demo/schema --config demo/schema-cfg --out-dir ./generated
Running sql-tutorial-configuration-based@0.1.0 (m2t) on demo/schema
decision OutputLayout -> SingleFile
decision IdentifierQuoting -> Unquoted

One file this time, Library_rel.sql:

-- SQL DDL generated by Synthesis from Library_rel
 
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER REFERENCES Author(authorId)
);
 
CREATE TABLE Author (
  authorId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  authorName VARCHAR(255)
);
 
CREATE TABLE Category (
  categoryId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  categoryName VARCHAR(255)
);
 
CREATE TABLE categorizedAs (
  BookId_FK INTEGER NOT NULL REFERENCES Book(bookId),
  CategoryId_FK INTEGER NOT NULL REFERENCES Category(categoryId)
);

That is byte for byte what Part 1's transformation produced from the same schema, header line included, with the REFERENCES clauses back inside the column definitions where inlineReferences put them. Part 1 is not superseded by this package; it is contained in it.

Note that neither announcement carries (default) any more, including IdentifierQuoting -> Unquoted, which selects the same option the default run did. The configuration says Unquoted explicitly, and an explicit choice is not a fallback even when it agrees with one.

FilePerTable​

The same two-line edit again, pointing at FilePerTable:

Running sql-tutorial-configuration-based@0.1.0 (m2t) on demo/schema
decision OutputLayout -> FilePerTable
decision IdentifierQuoting -> Unquoted
Wrote <out-dir>/Book.sql
Wrote <out-dir>/Author.sql
Wrote <out-dir>/Category.sql
Wrote <out-dir>/categorizedAs.sql
Wrote <out-dir>/Library_rel-constraints.sql

Five files from a transformation whose only change was one reference in one configuration model. Each table file is a header and one statement:

-- Table Book of Library_rel, generated by Synthesis
 
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER
);

Library_rel-constraints.sql is unchanged from the default run, because filePerTableLayout and tablesAndConstraintsLayout call the same constraintsDocument helper. The file names come from <Doc name=...>, which the option built from tab.name, so categorizedAs.sql keeps the schema's own casing.

DoubleQuoted, and two issues composing​

Back to the default layout, and this time edit the other <Choice>, the one whose issue is IdentifierQuoting:

Running sql-tutorial-configuration-based@0.1.0 (m2t) on demo/schema
decision OutputLayout -> TablesAndConstraints
decision IdentifierQuoting -> DoubleQuoted

Every identifier in Library_rel.sql is now wrapped:

CREATE TABLE "Book" (
  "bookId" INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  "bookTitle" VARCHAR(255),
  "AuthorId_FK" INTEGER
);

and so is every identifier in the constraints file, including the constraint names, which foreignKeyToAlter also passes through quoteIdentifier:

ALTER TABLE "Book" ADD CONSTRAINT "fk_Book_AuthorId_FK"
  FOREIGN KEY ("AuthorId_FK") REFERENCES "Author"("authorId");

Now set both: FilePerTable and DoubleQuoted together.

Running sql-tutorial-configuration-based@0.1.0 (m2t) on demo/schema
decision OutputLayout -> FilePerTable
decision IdentifierQuoting -> DoubleQuoted
Wrote <out-dir>/Book.sql
Wrote <out-dir>/Author.sql
Wrote <out-dir>/Category.sql
Wrote <out-dir>/categorizedAs.sql
Wrote <out-dir>/Library_rel-constraints.sql
-- Table Book of Library_rel, generated by Synthesis
 
CREATE TABLE "Book" (
  "bookId" INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  "bookTitle" VARCHAR(255),
  "AuthorId_FK" INTEGER
);

Read the first two lines of that file carefully. The file is still Book.sql and the comment still says Table Book, while the SQL inside says "Book". Neither of those is an oversight and neither needed a rule to keep them straight: quoteIdentifier is called on the identifiers that go into statements, and a file name is not a SQL identifier, so filePerTableLayout builds <Doc name={...}> from tab.name directly. The two issues compose because each of them only touches the thing it is about.

Configurations do not have to be complete​

Delete the whole <GlobalChoice name="gc_IdentifierQuoting"> block from the configuration, leaving only the layout choice, and the run still works:

Running sql-tutorial-configuration-based@0.1.0 (m2t) on demo/schema
decision OutputLayout -> SingleFile
decision IdentifierQuoting -> Unquoted (default)

An issue a configuration says nothing about falls back to the option the decision model marks as default, and never silently: the fallback is announced with (default) and materialized as a real choice, so the configuration that actually ran is always inspectable. --default-configs governs only the case where there is no configuration at all.

Before executing, a configuration is checked twice over. Nominally: the transformation and version stamped in its header, its binding model and its source model must all match this run. Structurally: every choice's issue must exist in the decision model, every selected option must belong to its issue, and no issue may be covered twice. The configurations guide states both levels in full.

Reading the (default) marker​

One detail is worth knowing before it surprises you. With the layout switched to SingleFile and quoting left at Unquoted, config show and the run print the second line differently:

  decision IdentifierQuoting -> Unquoted (default)
decision IdentifierQuoting -> Unquoted

Both are correct, because they are answering different questions. config show reads a configuration model on its own and marks the options that the decision model flags as defaults, which is what you want when reviewing a file: it tells you which choices are the ones nobody would argue with. A run compares the configuration against the issues it has to resolve and marks only what it had to fall back on, which is what you want in a log: it tells you which decisions were made by absence.

One directory, for now​

Every layout on this page wrote its files side by side into --out-dir. That is the whole of what the CLI does with a document today: one <Doc> becomes one file, and every file lands directly under the output directory.

A fourth layout that grouped the files into folders is the obvious next option. The text metamodel has a Directory concept and the components file exports a Dir tag, and documents wrapped in one are written into that folder, so nothing prevents it. Adding it would mean one more @VarOption on documentLayout and no other change to the package, which is a fair summary of what declaring a design space buys: the set of admissible answers grows in one place, and every caller keeps working.

Where you are​

Three parts, one schema, and the same generator producing five different sets of files:

  • Part 1 wrote one file with a fixed template and no decorators.
  • Part 2 wrote two, by declaring named sections and placing content into them.
  • Part 3 writes whichever of those two, or one file per table, because the layout stopped being something the transformation knew and became something it asks.

The mechanism was the model-to-model tutorial's, used at a scale it did not demonstrate. There, an issue was raised per element and a binding model with a condition decided which elements raised it. Here, both issues are raised once per run, so the binding model is empty, the configuration is two choices long, and the decision is taken before the first character is generated. The decorators, the manifest, and the consent policy are identical in both.

What a run cannot do yet is chain: generating the relational schema from an EER model and then generating DDL from it are two commands, each with its own configuration. The pipelines guide covers packaging that chain as one artifact. The tutorial overview describes what each part adds.
