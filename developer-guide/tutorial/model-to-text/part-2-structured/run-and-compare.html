3. Run and compare

The package is the one Part 1 built, with a reorganized template and two new rules. Nothing about packaging it or running it has changed.

The manifest​

{
  "kind": "m2t",
  "entry": "./dist/transformation.js",
  "exportName": "RelToSqlStructuredTransformation",
  "source": {
    "metamodel": "rel-tutorial-metamodel"
  },
  "target": {
    "metamodel": "text"
  }
}

Field for field the same as Part 1's, except for exportName, which names this part's class. The number of files a transformation produces is not something the manifest knows or needs to know: it follows from the documents in the result.

Build, install, run​

npm run build

synth init
synth namespace mk demo
synth model import sample/library-rel.tsx --as demo/library-rel

synth transformation install .
synth transformation run sql-tutorial-structured --in demo/library-rel --out-dir ./generated
Running sql-tutorial-structured@0.1.0 (m2t) on demo/library-rel
Wrote /home/you/work/generated/Library_rel.sql
Wrote /home/you/work/generated/Library_rel-constraints.sql

Two documents, two Wrote lines, in the order the documents appear in the template. The sample model is the same file Part 1 used, so if you still have demo/library-rel in your workspace from Part 1 there is nothing to import again.

The tables file​

cat generated/Library_rel.sql
-- Tables of Library_rel, generated by Synthesis
 
CREATE TABLE Book (
  bookId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  bookTitle VARCHAR(255),
  AuthorId_FK INTEGER
);
 
CREATE TABLE Author (
  authorId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  authorName VARCHAR(255)
);
 
CREATE TABLE Category (
  categoryId INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  categoryName VARCHAR(255)
);
 
CREATE TABLE categorizedAs (
  BookId_FK INTEGER NOT NULL,
  CategoryId_FK INTEGER NOT NULL
);

Beside Part 1's file, three differences and no more.

  • The header comment is different text, from a different header section.
  • AuthorId_FK INTEGER has lost its REFERENCES Author(authorId), and the two join table columns have lost theirs. The columns and their NOT NULL clauses are untouched: a foreign key column is still a column, and the constraint is what moved.
  • Everything else is identical, including the order of the tables, which is still the order they appear in the schema.

The constraints file​

cat generated/Library_rel-constraints.sql
-- Foreign key constraints of Library_rel, generated by Synthesis
-- Apply after Library_rel.sql: references may be circular, so
-- every table has to exist before any of them is constrained.
 
ALTER TABLE Book ADD CONSTRAINT fk_Book_AuthorId_FK
  FOREIGN KEY (AuthorId_FK) REFERENCES Author(authorId);
 
ALTER TABLE categorizedAs ADD CONSTRAINT fk_categorizedAs_BookId_FK
  FOREIGN KEY (BookId_FK) REFERENCES Book(bookId);
 
ALTER TABLE categorizedAs ADD CONSTRAINT fk_categorizedAs_CategoryId_FK
  FOREIGN KEY (CategoryId_FK) REFERENCES Category(categoryId);

Three foreign keys, which is the same three the inline clauses of Part 1 expressed: the one on Book that came from the 1:N relationship, and the two on the categorizedAs join table. foreignKeysOf walks the tables in schema order and the columns in table order, so the statements come out grouped by table without anything sorting them.

Each statement is two lines and a separator, because each statement section holds three paragraphs. The continuation line is indented by the two spaces at the front of its template literal.

Applied in order, the two files produce the schema Part 1's single file produced. The difference is that they also produce it for schemas whose references are circular, which no single file with inline clauses can.

Running it as the second step of a chain​

The sample model is the output of eer-tutorial-basic, so this generator can be run as the second step of a chain in exactly the way Part 1's can:

synth transformation run eer-tutorial-basic sql-tutorial-structured \
  --in demo/library --out-dir ./generated

An EER schema goes in and two SQL files come out, with the relational schema existing only in memory between the steps.

The complete source​

Every listing in this part is a fragment of one file. Here it is whole, embedded from examples/tutorial/sql-tutorial-structured at build time, so what you read is exactly what the smoke test runs:

/** @jsx createExprNode */

/**
 * Model-to-text tutorial, Part 2: the same DDL, in two files instead of
 * one. Every <Doc> in an M2T model becomes one file, so a second file is
 * a second document and nothing more.
 *
 * The split is not cosmetic. Foreign keys can be circular (two tables
 * referencing each other, or a table referencing itself), so no ordering
 * of CREATE TABLE statements can satisfy every inline REFERENCES clause.
 * Production DDL creates every table first and adds the foreign keys
 * afterwards with ALTER TABLE. The document structure follows the
 * deployment order.
 *
 * The template reads the model once, builds each statement as a named
 * value, and then composes the two documents from those values. The
 * final expression is the file structure, which is the point: what the
 * transformation produces can be read without following a rule anywhere
 * else.
 */
import { createExprNode } from '@aelastics/synthesis/jsx'
import { abstractM2M } from '@aelastics/synthesis/m2m'
import { M2T, Doc, Sec, P } from '@aelastics/synthesis/m2t'
import type { ModelStore } from '@aelastics/synthesis/store'
import * as m2tmm from '@aelastics/synthesis/m2t'
import * as rmT from 'rel-tutorial-metamodel/model'

/** One foreign key: the column that points, and the column it points at. */
type ForeignKey = {
  table: rmT.ITable
  column: rmT.IColumn
  targetTable: rmT.ITable
  targetColumn: rmT.IColumn
}

export class RelToSqlStructuredTransformation extends abstractM2M<rmT.IRelSchema, m2tmm.M2T_Model> {
  constructor(store: ModelStore) {
    super(store)
  }

  template(s: rmT.IRelSchema) {
    // Read the model once, up front: the tables to create, and every
    // foreign key that has to be added after they all exist.
    const tables = this.tablesOf(s)
    const foreignKeys = this.foreignKeysOf(s)

    // One section per statement. Each is an ordinary value, so the
    // documents below can be read as the files they produce.
    const createStatements = tables.map((tab) => {
      const cols = tab.columns ?? []
      return (
        <Sec name={`table_${tab.name}`}>
          <P>{`CREATE TABLE ${tab.name} (`}</P>
          {cols.map((c, i) => (
            <P>{`  ${this.columnLine(c)}${i < cols.length - 1 ? ',' : ''}`}</P>
          ))}
          <P>{');'}</P>
          <P>{' '}</P>
        </Sec>
      )
    })

    const alterStatements = foreignKeys.map((fk) => {
      const constraint = `fk_${fk.table.name}_${fk.column.name}`
      return (
        <Sec name={`constraint_${fk.table.name}_${fk.column.name}`}>
          <P>{`ALTER TABLE ${fk.table.name} ADD CONSTRAINT ${constraint}`}</P>
          <P>{`  FOREIGN KEY (${fk.column.name}) REFERENCES ${fk.targetTable.name}(${fk.targetColumn.name});`}</P>
          <P>{' '}</P>
        </Sec>
      )
    })

    // Two documents, so two files. Each states its whole content.
    const tablesFile = (
      <Doc name={`${s.name}.sql`}>
        <P>{`-- Tables of ${s.name}, generated by Synthesis`}</P>
        <P>{' '}</P>
        {createStatements}
      </Doc>
    )

    const constraintsFile = (
      <Doc name={`${s.name}-constraints.sql`}>
        <P>{`-- Foreign key constraints of ${s.name}, generated by Synthesis`}</P>
        <P>{`-- Apply after ${s.name}.sql: references may be circular, so`}</P>
        <P>{'-- every table has to exist before any of them is constrained.'}</P>
        <P>{' '}</P>
        {alterStatements}
      </Doc>
    )

    return (
      <M2T name={`${s.name}_sql`}>
        {tablesFile}
        {constraintsFile}
      </M2T>
    )
  }

  private columnLine(c: rmT.IColumn): string {
    const parts: string[] = [c.name, c.type]
    if (c.isKey) {
      parts.push('PRIMARY KEY')
    }
    if (c.isAutoincrement) {
      parts.push('AUTOINCREMENT')
    }
    if (!c.isNullable) {
      parts.push('NOT NULL')
    }
    return parts.join(' ')
  }

  private tablesOf(s: rmT.IRelSchema): rmT.ITable[] {
    return s.elements.filter((el) => this.context.store.isTypeOf(el, rmT.Table)) as rmT.ITable[]
  }

  // Every referencing column of the schema, paired with the table and
  // column it points at. A column is a foreign key exactly when it has a
  // reference, so this walk is the complete list.
  private foreignKeysOf(s: rmT.IRelSchema): ForeignKey[] {
    const tables = this.tablesOf(s)
    const keys: ForeignKey[] = []
    for (const table of tables) {
      for (const column of table.columns ?? []) {
        if (column.references) {
          keys.push({
            table,
            column,
            targetTable: this.tableOwning(s, column.references),
            targetColumn: column.references
          })
        }
      }
    }
    return keys
  }

  // A column does not know its table, so the table an ALTER TABLE
  // statement has to name is the one whose columns contain the
  // referenced column.
  private tableOwning(s: rmT.IRelSchema, col: rmT.IColumn): rmT.ITable {
    const owner = this.tablesOf(s).find((tab) => (tab.columns ?? []).some((c) => c.name === col.name))
    if (!owner) {
      throw new Error(`Column '${col.name}' is referenced but belongs to no table of schema '${s.name}'`)
    }
    return owner
  }
}

The package around it is four more files: package.json, tsconfig.json, synth.json, and the sample model under sample/. Nothing in it is generated or hidden.

Where you are​

You have taken one generator and changed how its output is organized, twice, without touching what it generates. Content is placed by name rather than by where its rule was written, and the file structure is declared in one readable place at the top of the template.

Which leaves an obvious question hanging. Part 1 committed to one file. Part 2 committed to two. Both are defensible, and nothing in a relational schema says which is right: a small schema deployed by hand wants one script, a schema with circular references needs the split, and a schema kept under review per table might want one file per table. The model cannot answer that, because it is a property of the project the DDL is deployed into.

A question the source model cannot answer is exactly what a variation point is for. Part 3 declares the layout as an issue with options, binds it to the source metamodel, and lets a configuration model close it per run.
