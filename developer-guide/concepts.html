Concepts

One idea underlies everything in Synthesis: a model is a value: the result of evaluating an expression. What you write in JSX is not the model; it is a term in a model expression algebra. Rendering the expression is the evaluation that produces the model. Every other concept in this guide (components, templates, transformation rules) is a disciplined way of writing such terms.

This page builds that idea up from one small example.

A model is the value of an expression​

A simple approval workflow, one Write task followed by two parallel Approve tasks, written as a model expression (imports and the JSX pragma elided; setup is covered in Building Model Instances):

const approval = (
  <Process name="Approval" store={store}>
    <Sequence>
      <Task name="Write" />
      <Parallel>
        <Task name="Approve 1" />
        <Task name="Approve 2" />
      </Parallel>
    </Sequence>
  </Process>
)

const model = approval.render(new Context())

The JSX expression is a tree of unevaluated element descriptions. render() evaluates it: each tag creates a typed model element, nesting becomes association, and the result is the model: an approval process in which Write is followed by two parallel approvals:

Expression and value are different things, and keeping them apart is what gives Synthesis its power: expressions can be abstracted over, passed around, and composed before they are ever evaluated.

The four operators​

Every model expression is composed from exactly four kinds of operators:

OperatorIn JSXWhat evaluation does
Model creationthe root model tag: <Process store={store}>, <EERSchema …>creates a model: a typed container with its own namespace and type schema, into which child elements are placed
Element creationelement tags: <Task>, <Kernel>, <Column>creates a typed element with its properties and connects it to its parent
Reference$refByName, $ref, $refByIDretrieves an existing element instead of creating one
ComputationTypeScript in { … }: map, conditionals, function callscomputes sub-expressions dynamically

The first two build structure. The third is what makes models true graphs rather than trees: nesting alone can only express containment, while a reference connects an element to something created elsewhere:

<Attribute name="PersonName">
  <Domain $refByName="string" />
</Attribute>

Here no new Domain is created; the existing element named string is looked up and connected. A reference must resolve to an element that exists when it is evaluated; an unresolvable name is a construction error, not a silent null. When the metamodel declares name scopes, resolution is scope-aware: a bare name is probed from the nearest enclosing scope outward, and a path such as Author/id reaches into a sibling scope. See References for the three reference forms and Name scopes for scoped resolution.

The fourth operator is where the host language comes in. Anything TypeScript can compute can appear inside { … }, as long as it produces model expressions of the type expected at that position. This single mechanism replaces the special-purpose loop/conditional constructs of conventional transformation languages, and it is what makes parameterization possible.

Templates define families of models​

Add parameters to an expression and it stops describing one model and starts describing a family of models. A parameterized model expression is a model template: a function returning a model expression, in algebraic terms an open term with free variables. Seen this way, what we ordinarily call "a model" written in JSX is just the boundary case: an expression with no parameters and no computation is a model literal, and always evaluates to the same model. The approval process at the top of this page is a model literal; here is the same workflow as a template:

const Approval = ({ doc, approvers, parallel }: IApprovalConfig) => {
  const tasks = Array.from({ length: approvers }, (_, i) =>
    <Task name={`Approve ${doc} ${i + 1}`} />)

  return (
    <Process name={`${doc} Approval`}>
      <Sequence>
        <Task name={`Write ${doc}`} />
        {parallel ? <Parallel>{tasks}</Parallel>
                  : <Sequence>{tasks}</Sequence>}
      </Sequence>
    </Process>
  )
}

Two instantiations, two structurally different models from the same definition: different element counts, different topology, different property values.

<Approval doc="Contract" approvers={3} parallel={true} /> produces a process with three parallel approvals:

Higher-order templates​

Because templates are ordinary functions, they compose like functions, and nothing stops a parameter from itself being a template. A higher-order template takes another template as a parameter and abstracts over the structure of its sub-expressions, not just their property values.

First define the writing step as a template of its own, outside any workflow:

const Write = () => <Task name="Write" />

const ReviewedWrite = () => (
  <SubProcess name="WriteDocument">
    <Task name="Draft" />
    <Task name="ReviewDraft" />
  </SubProcess>
)

Then define the workflow as a higher-order template whose parameter is the whole task template (both definitions above qualify as Template<IActivity>, the common activity supertype):

const Approval = (WriteStep: Template<IActivity>) =>
  ({ doc, approvers }: { doc: string; approvers: number }) => (
    <Process name={`${doc} Approval`}>
      <Sequence>
        <WriteStep />
        <Parallel>
          {Array.from({ length: approvers }, (_, i) => <Task name={`Approve ${i + 1}`} />)}
        </Parallel>
      </Sequence>
    </Process>
  )

Evaluation now happens in two steps. Applying the higher-order template to a task template yields an ordinary template; supplying the remaining parameters closes the expression into a model literal, which renders to the model:

const SimpleApproval = Approval(Write)                            // a template
const contract = <SimpleApproval doc="Contract" approvers={2} />  // a model literal
const model = contract.render(new Context())                      // the model

Swapping the step swaps structure, not just values: Approval(ReviewedWrite) produces workflows whose writing step is a two-task sub-process, without touching the workflow skeleton:

A value parameter (like parallel above) selects among shapes the template already contains; a template parameter supplies the shape. (A fixed step can also be passed as a ready-made expression value, const write = <Task … />, and embedded with {write}; the template form shown here is the general one, constructing the step fresh at every use and admitting parameters of its own.) This exact construction ships executable in the workflow example suite; the Templates guide embeds it and shows how to run it.

Transformations are templates over a source model​

A model-to-model transformation is a template whose parameter is a source model. It is written as a class: its template method is the top-level rule, receiving the whole source model and iterating over its elements with the computation operator, and every further rule is a typed method from one source element to a target model expression:

export class Eer2Rel extends abstractM2M<em.IEERSchema, rmT.IRelSchema> {
  template(s: em.IEERSchema) {
    return (
      <RelSchema name={`${s.name}_rel`} store={this.context.store}>
        {s.elements
          .filter((el) => this.context.store.isTypeOf(el, em.Entity))
          .map((el) => this.entityToTable(el as em.IEntity))}
        ...
      </RelSchema>
    )
  }

  @E2E()
  entityToTable(e: em.IEntity): ExprNode<rmT.ITable> {
    return (
      <Table name={e.name}>
        {e.attributes.map((a) => this.attributeToColumn(a))}
      </Table>
    )
  }

  ...
}

The three dots elide the rest of a real transformation: inside template, the sibling iterations (relationships, in this example), and below entityToTable, the further rules and helpers they invoke (attributeToColumn, the relationship rules, type mapping). The model-to-model tutorial builds this exact class in full.

Each rule is a template like any other, with the computation operator iterating over the source element's properties and invoking further rules. Executing the transformation evaluates template's expression in a fresh target model; every rule invocation is recorded in a trace linking each target element back to the source elements it came from, giving bidirectional traceability for free.

Rule selection can be made subtype-aware: a rule marked as a specialization point dispatches on the runtime type of its source element, so each subtype gets its own rule instead of a branch inside a single rule. This is the mechanism behind Polymorphic Rule Dispatch. The full authoring workflow is in Writing Transformations.

Model to model, and model to text​

A transformation's target can be another model or it can be text, and Synthesis treats those as the same kind of thing.

A model-to-model transformation (m2m) produces a model of the target metamodel: an EER schema becomes a relational schema, whose elements are ordinary model elements you can query, transform again, or store in the workspace.

A model-to-text transformation (m2t) produces text, and it does so by targeting the engine's text-document metamodel, whose concepts are documents, sections, and paragraphs. Generating SQL means building a document expression whose paragraphs happen to contain SQL. Nothing about the rules changes: they are the same typed functions returning JSX over a target metamodel's components.

The difference is what happens to the result. An m2m result is written back into the workspace as a model, with a provenance header recording what produced it. An m2t result is serialized to files in a directory. A transformation package declares which kind it is in its manifest, and the two compose: a chain may pass models from step to step and end with a text step, because text is terminal. The model-to-text tutorial builds a generator this way, consuming exactly what the model-to-model tutorial produces.

Configuration-based transformations​

Some transformations contain genuinely open design choices: whether a 1:N relationship becomes a foreign key or a join table, how identifiers are quoted, how generated output is laid out across files. Synthesis makes such a choice a first-class model rather than a hidden flag. A decision model declares the design space: its issues and the options each issue offers, globally or per source element. A configuration model records the choices made for one specific source model. A configuration-based transformation is then a template over two parameters, the source model and a configuration model: a rule with variants is written as a variation point, and the recorded choice selects which variant runs.

Because configurations are models, everything already said about models applies: they are validated (against the decision model, its binding to metamodel concepts, and the input model), default configurations can be generated from the decision model's declared defaults, and every choice applied during a run is announced. The mechanism, decorators included, is in the Design Decisions in Transformations guide; the tutorials each build one configuration-based rule, for model-to-model and model-to-text transformations.

Metamodels are type schemas​

A metamodel in Synthesis is a type schema: a set of runtime types (defined with @aelastics/types) that constrains the algebra. It determines which tags exist, which properties they take, which children may appear where, and which subtype hierarchies rules can dispatch over. Conformance is not an afterthought checked by a separate validator: a well-typed expression evaluates to a model that conforms to its schema. TypeScript checks what it can statically, and the model store enforces type conformance on every connection at runtime. The authoring workflow is in Defining Metamodels, and the components that give a metamodel its JSX tags are covered in JSX Components.

Two guarantees are worth knowing by name:

  • Type preservation: evaluating a well-typed model expression yields a model conforming to its type schema.
  • Type-safe execution: if the source model conforms to the source schema and every rule produces well-typed target expressions, the transformation result conforms to the target schema.

Together they mean conformance is preserved compositionally: you get a valid target model because every step preserves validity, not because a final check happened to pass.

Models all the way down​

A model is itself a model element. Two useful consequences follow, with no extra machinery:

  • Models can contain other models: a model of models (a megamodel), used to organize collections of interrelated models.
  • An element's property can store a qualified name that designates an element in another model, like a foreign key. Models built from such references (weaving models) capture typed correspondences between independent models; transformation traces and cross-model links are built on this.

Formal background​

The algebra sketched here is developed rigorously, with full definitions, the type constructor system, conformance, evaluation semantics, and proofs of the properties named above, in the companion paper:

S. Nešković and D. Stojimirović, Models as Values in a Model Expression Algebra: A Functional Approach to Model Driven Engineering.

The paper is the formal foundation of the approach; this documentation describes the current implementation, which has continued to evolve since the paper was written. Where tooling details differ, the documentation is authoritative for practical use.
