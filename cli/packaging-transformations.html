Packaging Transformations

Under development

The packaging workflow described below is part of the planned synth CLI and is not yet implemented.

This page explains how to take a transformation you have written (see Writing Transformations) and turn it into a package others can install with synth tx install.

Design summary​

ConcernChoice
Distribution channelPublic npm registry
Metamodel handlingSeparate packages, referenced as dependencies
Version isolationOne installed version per transformation name in a workspace
Manifest formatSeparate synth.json file (not embedded in package.json)

The package is npm-compatible — synth tx install accepts npm names, git URLs, local directories, and .tgz tarballs. Authoring uses standard npm tooling plus a few synth tx helpers.

Project layout​

A transformation project produced by synth tx init has this shape:

my-eer-to-relational/
├── package.json              # npm metadata, dependencies
├── synth.json                # Synthesis-specific manifest (see below)
├── tsconfig.json
├── src/
│   ├── transformation.ts     # the @M2M class
│   └── index.ts              # re-exports
├── test/
│   └── fixtures/             # sample source models
├── dist/                     # compiled output, generated by `synth tx build`
│   ├── transformation.js
│   ├── transformation.d.ts
│   └── synth.json            # copy of the manifest, frozen at build time
└── README.md

The dist/ directory is the artifact that ships. Source files (src/, test/) are not required at install time.

The synth.json manifest​

The manifest declares everything synth needs to discover, validate, and run the transformation without loading code.

{
  "name": "eer-to-relational",
  "version": "1.2.0",
  "engines": { "synth": ">=0.3.0" },
  "entry": "./dist/transformation.js",
  "exportName": "EERToRelational",
  "source": {
    "metamodel": "@aelastics/eer-metamodel",
    "versionRange": "^2.0.0"
  },
  "target": {
    "metamodel": "@aelastics/relational-metamodel",
    "versionRange": "^1.0.0"
  },
  "variability": {
    "issues": [
      {
        "id": "inheritance-strategy",
        "label": "Inheritance mapping",
        "options": ["single-table", "joined", "table-per-class"],
        "default": "joined"
      }
    ]
  }
}

Field reference​

FieldTypePurpose
namestringIdentifier used by synth tx install, synth run, etc. Should match the npm package name without scope.
versionstring (semver)Version of the transformation. Mirrors package.json#version.
engines.synthsemver rangeRequired synth CLI version. The installer rejects packages whose range excludes the running CLI.
entrystring (path)Path to the compiled JS file that exports the transformation class. Relative to the package root.
exportNamestringNamed export of the transformation class. The CLI does require(entry)[exportName].
source.metamodelstringPackage name of the source metamodel.
source.versionRangestring (semver)Required version range of the source metamodel.
target.metamodelstringPackage name of the target metamodel.
target.versionRangestring (semver)Required version range of the target metamodel.
variability.issuesarrayOne entry per @VarPoint declared in the transformation. id must match the issue id in code. options lists the allowed @VarOption names. default is consulted by synth config init.

source and target reference metamodels by package name plus semver range. The installer resolves the actual version at install time and records it in the workspace registry. If a compatible version is not already installed, the user is prompted to install it.

Author workflow​

# 1. Scaffold a new transformation project
synth tx init eer-to-relational
cd eer-to-relational

# 2. Edit src/transformation.ts and synth.json

# 3. Build — compiles TypeScript, validates the manifest, copies it into dist/
synth tx build

# 4. Test against fixtures in test/
synth tx test

# 5. Produce a tarball for distribution
synth tx pack
# → eer-to-relational-1.2.0.tgz

# 6. Publish to npm (passthrough to `npm publish`)
synth tx publish

What synth tx build does​

  1. Runs the TypeScript compiler against src/, output to dist/.
  2. Validates synth.json against the manifest schema.
  3. Confirms entry resolves to a file containing exportName.
  4. Confirms the issue ids in variability.issues correspond to @VarPoint decorators in the compiled code.
  5. Copies the validated synth.json into dist/ so it ships with the compiled output.

What synth tx pack does​

Wraps dist/, synth.json, package.json, and README.md into an npm-style tarball. The tarball is what gets installed regardless of source (npm registry, git, or local).

Install resolution​

synth tx install <source> accepts any of:

SourceExampleBehavior
Published npm package@aelastics/eer-to-relational@^1.2Fetched from the configured registry.
Git URLgit+https://github.com/user/repo.git#v1.2.0Cloned and built if dist/ is missing.
Local directory./my-eer-to-relationalUsed in place during development. Re-runs synth tx build if source is newer than dist/.
Local tarball./eer-to-relational-1.2.0.tgzExtracted into the workspace.

After install, the package lands at <workspace>/tx/<name>/. Its metamodel dependencies are resolved using source.metamodel and target.metamodel. If a required metamodel is not yet installed, the user is offered:

This transformation requires @aelastics/eer-metamodel ^2.0.0.
Install it now? [Y/n]

One version per name​

A workspace holds one installed version of each transformation. Installing a different version replaces the existing one; synth tx ls shows what is currently installed.

synth tx install eer-to-relational@1.2.0      # installs 1.2.0
synth tx install eer-to-relational@2.0.0      # replaces 1.2.0 with 2.0.0

This keeps synth run eer-to-relational unambiguous. If side-by-side versions become necessary, support will be added in a future release.

Compatibility with the CLI​

The engines.synth field in the manifest is checked at install time. A package declaring "engines": { "synth": ">=0.3.0" } will refuse to install on synth 0.2.x. Authors should bump this range when relying on newly introduced CLI features.
